# iOS LLM runtime for background cleanup

Researched 2026-09-28. Extends `ios-platform-constraints.md` §7 and `bench-cleanup-llm.md` (already-known facts are not repeated at length; changes/corrections to those are called out below). Labels: **[Doc]** Apple documentation. **[Reported]** a developer/shipping app says so. **[Unverified]** inference or a single unconfirmed source.

## TL;DR

- **GPU/Metal is blocked for every iPhone in the background, full stop.** Apple DTS (Kevin Elliott, Sept 2025): background GPU (`BGContinuedProcessingTask` + `continued-processing.gpu`) works only on **iPads with M3 or better**; "that device does not support background GPU access" on any iPhone tested, including iPhone 16 Pro Max — no extra entitlement fixes it ([forum 801229](https://developer.apple.com/forums/thread/801229), 2025-09; corroborated on iPhone 15 Pro/16 Pro at [forum 816774](https://developer.apple.com/forums/thread/816774)). There is **no exception for an app with an active audio-recording session** — nothing in Apple's docs or any forum/issue ties GPU permission to audio-session state; it's a hardware/OS gate, not a per-app-state one. Real crashes confirm this in practice, active audio or not: `error: Insufficient Permission (to submit GPU work from background) (00000006:kIOGPUCommandBufferCallbackErrorBackgroundExecutionNotPermitted)` ([llama.cpp #16998](https://github.com/ggml-org/llama.cpp/issues/16998), 2025-11; [mlx-swift-examples #230](https://github.com/ml-explore/mlx-swift-examples/issues/230), 2025-03, MLX maintainer confirms "expected... Metal is not allowed to run in background"). **So MLX (Metal), llama.cpp's Metal backend, MLC-LLM, and Cactus's default GPU path cannot run while wippr is backgrounded.**
- **`com.apple.developer.background-tasks.continued-processing.inference` (iOS 27) gates ALL background Neural Engine access, not just `BGContinuedProcessingTask` work.** Apple's own doc: "The system also requires the entitlement for any Neural Engine access while your app is in the background, regardless of whether it's running a continued background task. You can perform inference with Core AI, Core ML, or Metal Performance Shaders Graph." ([doc](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.background-tasks.continued-processing.inference), copyright 2026). It appears **self-service**: KeyVox's shipped `.entitlements` file just declares it `<true/>` next to ordinary entitlements (iCloud, App Groups) — no special Apple-approval workflow is documented or evidenced anywhere for it, unlike genuinely restricted entitlements.
- **CPU is the only unconditionally-safe background backend.** llama.cpp's CPU path (NEON, i8mm, optional Arm KleidiAI; **SME specifically is unconfirmed on any iPhone chip** — see §1 correction) needs no entitlement and is what KeyVox itself ships for its own on-device text cleanup (a LoRA on Qwen2.5-0.5B, GGUF, via a vendored `llama.xcframework`).
- **Apple's new Core AI (iOS 27)** is a real, general path to run your own small LLM through the same `LanguageModelSession` API as Foundation Models — Apple ships export recipes for Qwen3 0.6B/1.7B/4B/8B — but it picks GPU/CPU/ANE per export, so the same background rules above apply, and its iOS KV cache is capped at **1,024 tokens** (fine for our ~150–600 prompt + 64 output budget).
- **New 2026 dictation-cleanup fine-tunes exist beyond S1-mini** (all independently verified live on Hugging Face, 2026-09-28): `DRTR-J/amnis-light-cleanup-en-v1`, `flowcorp-ch/BudgieScribe-Nano`, `SpeakoFlow/speakoflow-mini` — all Qwen3-0.6B/Qwen3.5-0.8B, GGUF Q4_K_M, 378–542 MB. Worth a bench run alongside S1-mini.
- **Recommendation unchanged in substance, refined in mechanism**: llama.cpp CPU-only (NEON+i8mm, KleidiAI where available) running S1-mini/BudgieScribe-class Qwen3-0.6B Q4_K_M via a vendored `llama.xcframework` is the only path with zero background risk and no new entitlement. Core AI on ANE (with the inference entitlement declared) is the best-integrated fallback if we're willing to ship a new entitlement and re-test each iOS point release, per KeyVox's own experience of it breaking across 27 betas.

## 2. `continued-processing.inference`: self-service, and scope is broader than `BGContinuedProcessingTask`

- **Scope [Doc]**: confirmed directly from Apple's entitlement page (DocC JSON, copyright 2026, iOS 27.0+): the entitlement is required for **any** Neural Engine access while backgrounded, "regardless of whether it's running a continued background task." It covers Core AI, Core ML, and Metal Performance Shaders Graph specifically. So a plain `UIBackgroundModes=audio`-kept-alive app (wippr's case, no `BGContinuedProcessingTask` involved) needs exactly this one entitlement to touch the ANE — nothing more.
- **Approval [Reported, no counter-evidence found]**: no Apple doc, WWDC session, or forum thread describes a request/approval workflow for this entitlement (unlike, e.g., Endpoint Security or Family Controls, which explicitly require Apple sign-off). The companion `continued-processing.gpu` entitlement's doc explicitly says "add the Background GPU Access capability to your target in Xcode" — ordinary self-service. **KeyVox's own shipped `.entitlements` file** (`iOS/KeyVox iOS/KeyVoxiOS.entitlements`, fetched via GitHub API 2026-09-28) lists `com.apple.developer.background-tasks.continued-processing.inference` = `true` in the same flat list as its iCloud key-value store and App Group entitlement — no sign of a special profile. Treat as self-assignable; **still worth a real Xcode Signing & Capabilities check**, since Apple hasn't published a named "capability" toggle for it the way it did for GPU.
- **KeyVox's real history** (`iOS/CHANGELOG.md`, fetched 2026-09-28): v1.2.11–1.2.14 (2026, before 1.2.15) **routed Whisper/Parakeet Core ML encoders to a CPU-only compatibility path specifically to dodge an "iOS 27 beta ANE failure"** — i.e., before adding the entitlement, background ANE calls were being killed. **v1.2.15 (2026-07-15)**: "Added Apple's iOS 27 continued-processing inference entitlement so the existing Core ML speech-to-text path can use the Neural Engine while KeyVox is executing in the background," restoring ANE and fixing "iOS 27 background Whisper and Parakeet Neural Engine requests being canceled when the app had otherwise valid background execution time." This is the closest real precedent to wippr's exact situation (audio-session-kept-alive background app, ANE inference, no `BGContinuedProcessingTask`), and it confirms the entitlement is necessary **and sufficient** for that case.
- **KeyVox's own cleanup model** (not ASR): its "Vibes" rewrite ships as a **LoRA adapter on `Qwen/Qwen2.5-0.5B-Instruct`**, trained with `mlx_lm.lora` (rank 16, MLX training scale 40 → llama.cpp runtime scale 32, i.e. `lora_alpha = 32 × rank`), converted to GGUF, and run through **`KeyVoxLocalInference`**, a Swift package whose only dependency is a vendored `llama.xcframework` binary target (`Packages/KeyVoxLocalInference/Package.swift`, fetched 2026-09-28). This is CPU llama.cpp, not Core AI/Core ML — for its own text-cleanup step KeyVox uses the same architecture this doc recommends for wippr (§5).

## 3. GPU access with an active audio-recording session: no exception found

Direct question: does the "orange pill" background-audio exception (which lets wippr's process keep running) also unlock Metal/GPU? **No evidence anywhere that it does; strong evidence that it doesn't.**

- DTS Kevin Elliott ([forum 801229](https://developer.apple.com/forums/thread/801229), Sept 2025): "No 'extra' approval or configuration is needed for background GPU access on any device that supports it. The problem here is actually this: that device does not support background GPU access" — supported devices are **iPads with M3 or better only**; no iPhone, including iPhone 16 Pro Max, supports it. This is a hardware/OS capability gate, independent of entitlements, app state, or why the app is backgrounded.
- [Forum 816774](https://developer.apple.com/forums/thread/816774) (2025-2026): same conclusion tested on iPhone 15 Pro and 16 Pro; WWDC26 claimed "your continued processing tasks can also benefit from background GPU access on supported devices" but "no iOS devices appear to support it."
- Real crashes match exactly, and none of them are audio-session-specific — they trigger from any backgrounded Metal call: llama.cpp [#16998](https://github.com/ggml-org/llama.cpp/issues/16998) (2025-11, iOS 18.7.1, `llama_decode` from Swift, app minimized) and mlx-swift-examples [#230](https://github.com/ml-explore/mlx-swift-examples/issues/230) (2025-03). A commenter on the llama.cpp issue (shahamitj, 2025-11-06) notes even the sanctioned path only "works when the user's device is iOS 26 and the function is called in `BGContinuedProcessingTask` with an implementation of Live Activity" — and per §3 above, that path itself excludes iPhone hardware anyway.
- A llama.cpp maintainer patch ([#20306](https://github.com/ggml-org/llama.cpp/pull/20306), merged 2026-03-09, verified directly) makes the library **survive** the GPU revocation (sticky error flag, `GGML_STATUS_FAILED`, recreate backend to recover) instead of hard-aborting — useful defensively if we ever call into Metal accidentally from a background code path, but it does not restore GPU access.
- **Conclusion**: plan wippr's background LLM step as CPU-only, unconditionally. There is no known device, entitlement, or app-state combination that gives an iPhone GPU access while backgrounded.

## 5. Recommendation

**Runtime + backend + quant: llama.cpp, CPU-only (NEON + i8mm, KleidiAI if the build supports it), Q4_K_M, S1-mini or `BudgieScribe-Nano-en` (Qwen3-0.6B class).** Rationale:
- It is the *only* combination in §1 with **zero background risk on any iPhone** — no entitlement, no device-capability gate, no BGContinuedProcessingTask, nothing Apple could restrict further in an OS update without breaking `UIBackgroundModes=audio` itself.
- It already meets budget: 0.8 s warm / 0.9 s cold for the 60-word case on a 4-thread desktop proxy (`bench-cleanup-llm.md`); real iPhone 0.6B decode figures across runtimes cluster 116–390 tok/s even on GPU/ANE paths, so CPU-only NEON+i8mm (not directly benchmarked on iPhone in any 2026 source found — flag as our own bench's job) should comfortably clear ~64 tok/s needed for 64 tokens in under 1 s once i8mm/SME kernels are confirmed enabled in the build.
- **Concrete integration path, mirroring KeyVox's shipped architecture** (`Packages/KeyVoxLocalInference/Package.swift`, verified 2026-09-28): vendor a prebuilt `llama.xcframework` (build from [ggml-org/llama.cpp](https://github.com/ggml-org/llama.cpp) with `GGML_METAL=OFF`, CPU backend only, optionally `GGML_CPU_KLEIDIAI=ON` on supported Arm toolchains) as a Swift Package `.binaryTarget`, wrap it in a thin Swift module (`llama_backend_init` / `llama_model_load` / `llama_decode` on a background `Task`, `n_threads` tuned to the phone's performance cores), ship the S1-mini or BudgieScribe GGUF (378–484 MB) as a bundled resource, and — if we later want a LoRA-over-shared-base approach to cut app size — apply KeyVox's exact pattern (MLX-trained LoRA, rank 16, `lora_alpha = 32 × rank` at llama.cpp runtime scale, merged or applied at load).
- **Do not** put the cleanup step on MLX, MLC-LLM, or Cactus's default path: all three are Metal-primary on iOS and will crash or silently fail the moment the app is backgrounded (§1, §3), regardless of any entitlement we hold.
- **Consider Core AI (ANE) as a v2 path**, not v1: it needs shipping the new `continued-processing.inference` entitlement (self-service per §2, but untested by us on a real device) and re-validating every iOS 27 point release, mirroring KeyVox's own churn (CPU-only fallback → entitlement → restored ANE across versions 1.2.11–1.2.15). Its upside is Apple-maintained export tooling (`coreai-torch`, Qwen3 recipes already published) and a documented 1,024-token iOS KV cap that we're well under. Do this only after llama.cpp CPU ships and only if profiling shows CPU is the latency or battery bottleneck.
- **Do not switch to Qwen3.5/Qwen2/4B-class models for the background path** — even the fastest GPU/ANE numbers in §1 (Qwen3.5-2B: 291.9 tok/s MLX, 149.7 tok/s llama.cpp GPU) are on Metal, which is unavailable to us; CPU-only at that size would blow the <1 s budget (consistent with `bench-cleanup-llm.md`'s existing verdict).
